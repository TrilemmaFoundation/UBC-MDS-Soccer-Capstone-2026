The Problem

Trilemma Foundation tracks European football performance but had no scalable way to answer:

  • Which players fit a specific tactical role?
  • Do players perform the same for club vs national team?
  • Which teams are in form right now?

Raw StatsBomb data exists — but it’s not queryable by analysts without complex SQL.

Success criteria:

  • Cluster players into tactical archetypes
  • Score club vs international consistency
  • Let analysts ask questions in plain English

Trilemma Foundation works with football performance data, but the raw StatsBomb event data — matches, events, and lineups across 15+ competitions — isn’t directly useful to analysts. You’d need complex SQL just to answer “who are the top pressing forwards this season?”

We turned that into three scientific objectives: cluster players into tactical archetypes, score club-vs-national consistency for scouting, and wrap everything in a natural-language chatbot so analysts don’t need SQL.

Consistency: The Question & Pipeline

Research Question 3: Do players perform differently for club vs national team?

  • Eligibility: ≥ 270 minutes in both contexts (~3 full matches)
  • Cohort: 493 dual-context players across 58 countries
  • Z-scores computed within each context (club peers vs club, national vs national)

We built club-vs-national consistency scoring for RQ3. Trilemma wanted to know whether strong club players show up the same way for their country. dbt builds int_player_club_vs_national, splitting stats by context and z-scoring 13 metrics within each. consistency.py weights z-scores with PCA loadings, computes scores and quadrants, and writes to BigQuery. Only players with 270+ minutes in both contexts qualify — 493 players across 58 countries.

Formulas & Quadrant Model

Step 1 — Z-score within context

\(z = \dfrac{\text{player\_value} - \text{mean\_in\_context}}{\text{stddev\_in\_context}}\)

Step 2 — Performance score (per context)

\(\text{performance} = \sum (z_{\text{feature}} \times \text{PCA weight})\)

Step 3 — Consistency score

\(\text{consistency} = 1 - \text{mean}(|z_{\text{club}} - z_{\text{nat}}|)\)

Step 4 — Quadrant (median splits on club & national performance)

Quadrant Definition
Elite Club ≥ median and national ≥ median
Club Specialist Club ≥ median, national < median
International Specialist Club < median, national ≥ median
Underperformer Both below median

Three metrics, each answering a different question. Performance scores are the x and y axes — weighted sum of z-scores using PCA weights. Higher means stronger vs peers in that context. Consistency score measures profile similarity across contexts — near 1 means similar style, not necessarily high quality. Quadrants split at medians, roughly 25% per bucket. Dashed lines on the plot are those cutoffs.

System Architecture: End-to-End

  • Ingestion: StatsBomb API → Google Cloud Storage (GCS)
  • Warehouse: Centralized in Google BigQuery
  • Transformation: 3-layer dbt architecture
  • Machine Learning: Python scripts for PCA/KMeans and consistency scoring
  • Serving layer: Django web app (Looker embed + natural-language chatbot)

Thanks Rabin. I’ll take you through how we built this engine. This is a high-level look at our end-to-end architecture. We extract open event data from the StatsBomb API and land it in Google Cloud Storage before loading it into BigQuery. From there, dbt handles all our SQL transformations, piping the clean data into our Python ML scripts for clustering and consistency scoring. Finally, the analytics-ready data is pushed to our serving layer: a Django web application that houses our interactive Looker Studio dashboard via an embedded iframe, alongside our natural-language chatbot.

The Data Pipeline

  • Raw data: gs://football-analytics-mds2026/ → raw_statsbomb
  • Staging (dbt_staging): 1:1 mirror of raw tables — type casts only
  • Intermediate (dbt_intermediate):
    • Filters for men’s football (gender = 'male')
    • Enforces ≥ 270-minute threshold for statistical stability
  • Marts (dbt_marts): Analytics-ready tables joined with ML outputs

Looking closer at the transformation pipeline, we adopted a strict three-layer dbt architecture. Raw StatsBomb parquet files land in our GCS bucket and BigQuery. Staging acts purely as a 1:1 mirror to clean up data types. The heavy lifting happens in the intermediate layer, where we aggregate per-90 metrics, apply our 270-minute playing threshold to remove statistical noise, and scope the current data to men’s competitions. Finally, our marts layer joins these transformations with the ML cluster assignments, producing the clean tables that Looker and our chatbot read from.

Automated Orchestration with Dagster

To keep the platform hands-off for Trilemma Foundation, we orchestrated the entire workflow using Dagster. Our asset graph ensures models and ML scripts only run when their upstream dependencies succeed. We have a weekly schedule set for Monday mornings at 6 AM UTC to refresh the entire pipeline. Additionally, if an analyst manually drops a new match file into the bucket, it automatically triggers a downstream refresh of the dbt models and ML outputs without getting stuck in an ingestion loop.

Natural Language Analytics Chatbot

  • Engine: Groq llama-3.3-70b-versatile LLM
  • Tool-calling loop: English → executable BigQuery SQL
  • Security: is_safe_sql blocks non-SELECT statements

Here is the chatbot in action. We wanted analysts to get immediate answers without needing to know BigQuery SQL. We engineered a Django-based chatbot utilizing a Groq LLM tool-calling loop. When a user asks a question, the llama-3.3-70b-versatile model translates the English prompt, queries BigQuery, and returns the formatted data. Security was paramount, so we implemented a custom is_safe_sql layer that aggressively blocks any non-SELECT statements. We also included an advanced debug mode so analysts can peek under the hood and verify the exact SQL the LLM generated.

Limitations & Future Scope

🧤 Goalkeeper filter

Goalkeepers excluded from PCA clustering — assigned cluster = -1, archetype Goalkeeper

📊 Polymarket odds

No automated ingestion script yet — relies on manual GCS uploads

⚽ Women’s football

Pipeline scoped to men’s competitions at the intermediate layer

→ Future: parallel dbt intermediate models when data is available

While the platform is robust, there are a few limitations we’ve identified for future work. First, goalkeepers have vastly different metrics than outfield players, so they are bypassed in our ML clustering and hardcoded to a specific archetype. Second, our Polymarket odds data currently requires manual uploading, as we haven’t automated that ingestion yet. Finally, because we enforce a gender filter at the intermediate layer to standardize the tactical models, bringing in StatsBomb’s women’s football data will require spinning up a parallel set of intermediate dbt models.
